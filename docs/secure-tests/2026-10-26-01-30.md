# Relatório de análise de segurança

## 1. Resumo executivo

- **Status:** Aprovado com ressalvas (findings upstream no aplicativo móvel)
- **Data (UTC):** 2026-10-26 01:30
- **Analista:** Devin
- **Escopo:** proteção anti-flood/anti-DoS do relay serverless
  (`lib/protection.ts`, integração em `api/*.ts`, `lib/onramp-validation.ts`,
  `api/onramp-session.ts`, `lib/cors.ts`, `vercel.json`, `lib/test-environment.mjs`),

Nenhuma vulnerabilidade crítica ou alta foi introduzida pelas alterações. Os
findings altos remanescentes são de dependências upstream do aplicativo móvel
(`zod` 3.x pinado por `@circle-fin/onramp-kit`, `node-forge`/`@expo/cli` sem
versão corrigida compatível) e permanecem documentados como risco aceito sob
decisão explícita do mantenedor — bloqueiam publicação até decisão formal.

## 2. Inventário revisado

- `relay/lib/protection.ts` — limiter atômico (Redis `EVAL` Lua) + fallback em
  memória limitada; 1 sinal/s por cliente, flood >10 tentativas/s por IP,
  cooldown quadrático `min(30s×n², 1h)`, reabilitação em 24h, orçamento HTTP
  600 req/min e orçamento de requisições inválidas >30/min.
- `relay/api/{signal,peers,tx-report,escrow-request,ban,health,stats,onramp-session}.ts`
  — integração de proteção antes do processamento; respostas 429/503 seguras
  com `Retry-After`, `retry_after_ms`, `cooldown_until`, `next_step`/`nest_step`.
- `relay/lib/onramp-validation.ts` — validação e limites de `assets.tokens`,
  `assets.chains`, `assets.pairs` antes do SDK Circle.
- `relay/lib/test-environment.mjs` — ambiente de teste isolado: remove
  `UPSTASH_*`/`KV_*`/`BAN_DAO_ADDRESS`/`CIRCLE_ONRAMP_API_KEY` e bloqueia
  `fetch` externo, garantindo que a suíte não dependa de rede nem de segredos.
- `rapport-crypto-p2p-chat/src/infrastructure/messaging/SignalScheduler.ts` e
  transportes — fila global por relay+carteira (64 jobs, expiração 60s,
  intervalo 1050ms), `AbortController` 15s, pausa em cooldown até 1h,
  polling limitado a 8 tópicos/ciclo sem sobreposição.
- `.gitignore` do relay — cobertura de `.env*` (preservando `.env.example`).

## 4. Provas / evidências

- Relay: `npm test` → **16/16** (inclui atomicidade Redis, paridade
  memória/Redis, fail-closed, contratos seguros); `npm run typecheck` limpo;
  `npm run test:e2e` → **142 testes Playwright aprovados** (3,6 min).
- App: `npm test` → **48 arquivos / 542 testes aprovados**;
  `npm run typecheck` limpo.
- `lib/test-environment.mjs` executado via `--import` garante que nenhum teste
  faz chamada externa real (`fetch` lança erro explícito).
- Nenhum segredo, chave privada, token ou PII adicionado a código, testes,
  logs ou documentação; `.env` permanece fora do versionamento.

## 5. Recomendações

1. Antes de publicar/implantar, decidir formalmente sobre SC-001/SC-002
   (aceite de risco ou espera por correção upstream).
2. Configurar `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` em produção
   — obrigatório para a proteção distribuída (fail-closed sem eles).
3. Complementar com proteção volumétrica na borda (CDN/WAF) — este trabalho
   cobre abuso em camada de aplicação.
4. Validar visualmente a mensagem de cooldown em dev build nativo Expo —
   pendente por ausência de runner E2E mobile no ambiente.
